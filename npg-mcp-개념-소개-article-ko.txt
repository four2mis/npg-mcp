NginxProxyGuard를 MCP로 관리하기: npg-mcp 서버의 개념과 설계

초록
이 글은 역방향 프록시 관리 도구인 NginxProxyGuard(NPG)의 REST API를 MCP(Model Context Protocol) 서버로 감싸, AI 에이전트(또는 LLM 기반 도구)가 자연어 명령만으로 프록시 호스트·인증서·보안 규칙·nginx 설정을 안전하게 관리할 수 있게 해주는 "npg-mcp" 서버의 개념과 설계를 설명한다.

1. 배경: MCP란 무엇인가?
MCP(Model Context Protocol)는 AI 애플리케이션이 외부 데이터와 도구에 표준화된 방식으로 접근할 수 있게 해주는 개방형 프로토콜이다. 쉽게 말하면 "AI를 위한 USB 포트"라고 할 수 있다. 각 서비스마다 제각각인 통합 방식을 도입하는 대신, MCP라는 공통 규격 위에 서버(도구 제공자)와 클라이언트(AI 에이전트)가 대화하도록 설계되었다.

MCP 서버는 여러 개의 "도구(tool)"를 노출한다. 각 도구는 이름과 JSON 스키마 기반의 인자 정의, 설명을 가지며, AI 에이전트는 이를 읽고 적절한 도구를 골라 호출한다. npg-mcp는 바로 이러한 MCP 서버 중 하나로, NginxProxyGuard의 관리 기능을 도구 형태로 노출한다.

2. 대상 시스템: NginxProxyGuard(NPG)
NginxProxyGuard는 Nginx 기반의 역방향 프록시 관리 패널로, 웹 UI 또는 REST API를 통해 다음을 관리할 수 있다:
- 프록시 호스트(도메인 → 백엔드 서버 매핑)
- SSL/TLS 인증서 (Let's Encrypt 등)
- 리다이렉트 호스트
- 보안 기능: 속도 제한(rate limit), 봇 필터, 보안 헤더, URI 차단, fail2ban, CAPTCHA/챌린지, 지리(Geo) 제한
- WAF(웹 방화벽) 및 익스플로잇 차단 규칙
- DNS/클라우드 제공자, 백업, API 토큰, 설정, 로그

이 모든 기능은 REST API(/api/v1/...)로 노출된다. npg-mcp는 이 REST API를 호출하는 "클라이언트"이자, 그 결과를 MCP 규격으로 다시 포장해 AI 에이전트에게 전달하는 "브리지" 역할을 한다.

3. 왜 MCP로 NPG를 관리하는가?
기존에는 NPG의 웹 UI를 직접 열거나 REST API를 curl/스크립트로 호출해야 했다. MCP 서버를 두면 다음과 같은 장점이 생긴다:
- 자연어 명령: "새 도메인 sub.example.com을 127.0.0.1:8080으로 연결하고 SSL을 켜줘" 같은 지시가 곧바로 API 호출로 해석·실행된다.
- 도구 발견성: 에이전트가 노출된 도구 목록과 설명을 읽고 스스로 올바른 작업을 선택한다.
- 일관된 오류 처리: MCP 계층에서 오류를 정리(sanitize)해 내부 호스트명이나 URL이 새지 않는다.
- 자동화: 사람이 UI를 만지지 않아도 반복 작업을 안전하게 자동화할 수 있다.

4. 아키텍처
npg-mcp는 FastMCP(파이썬 기반 MCP 구현)와 httpx HTTP 클라이언트로 구성된 파이썬 패키지이며, Docker 이미지로 배포된다.

구성 요소:
- npg_mcp/main.py: 108개 이상의 MCP 도구 정의와 인증 미들웨어, 전송 보안 설정
- npg_mcp/client.py: NPG REST API를 호출하는 HTTP 클라이언트 래퍼 (로그인 토큰 관리, 오류 정리 포함)
- Dockerfile / docker-compose.yml: 컨테이너 배포 (기본은 GHCR 사전 빌드 이미지 사용)

통신 흐름:
AI 에이전트 ⇄ HTTP/SSE (MCP, 포트 8081) ⇄ npg-mcp 서버 ⇄ NPG REST API(내부, npg-api:8080)

배포에는 두 가지 전송 방식이 지원된다:
- stdio 모드: 로컬에서 파이썬 모듈로 직접 실행
- HTTP 모드: uvicorn으로 HTTP 서버를 띄워 원격 에이전트가 접근 (기본)

5. 보안 설계
이 서버는 실제 인프라를 제어할 수 있으므로 보안을 중요하게 다룬다. 핵심 보안 장치:
- 전송 보안(Transport Security): MCP 표준의 TransportSecuritySettings를 이용해 DNS 리바인딩 보호를 기본 활성화하고, 허용 호스트(allowed_hosts)와 허용 오리진(allowed_origins)을 화이트리스트로 제한한다. 초기 구현이 보안을 완전히 해제한 모니키-패치를 쓰던 것을 제거하고, 환경변수(MCP_ALLOWED_HOSTS 등)로 유연하게 제어하도록 개선했다.
- 베어러 토큰 인증: MCP_API_TOKEN을 설정하면 모든 MCP 요청에 Authorization: Bearer <token> 헤더가 요구되며, 없으면 401을 반환한다. 노출된 네트워크 환경에서는 반드시 설정하도록 권장한다.
- 요청별 토큰: 공유 전역 토큰 대신 ContextVar 기반의 요청별 토큰을 사용해 동시 접속 클라이언트가 서로의 세션을 덮어쓰지 않게 한다.
- JWT 비노출: 로그인 도구가 원시 NPG JWT를 노출하지 않고, 성공 여부만 반환한다.
- 오류 정리(Error Sanitization): 내부 베이스 URL이나 호스트명이 예외 메시지를 통해 유출되지 않도록 고정 형식으로 정리한다.

6. 주요 도구 범주
108개 이상의 도구가 NPG 기능을 범주별로 노출한다:
- 인증: 로그인, 로그아웃, 내 정보
- 대시보드: 개요, 상태, GeoIP 통계
- 프록시 호스트: 조회·생성·수정·삭제·테스트·복제·동기화
- 보안(호스트별): 속도 제한, 봇 필터, 보안 헤더(프리셋 포함), 업스트림, URI 차단, fail2ban, 챌린지/CAPTCHA
- 지리 제한: 호스트별 조회·생성·수정·삭제
- 인증서: 조회·생성·삭제·갱신
- 리다이렉트/접근 목록/DNS/클라우드 제공자: CRUD
- WAF 및 익스플로잇 규칙: 목록·차단 해제·CRUD·토글
- 설정/로그/백업/API 토큰: 관리

7. 알려진 한계와 주의사항
- 실서비스 영향: 프록시 호스트를 생성·수정·삭제하면 실제 라우팅이 바뀌므로, 프로덕션 인프라에 적용하기 전에 반드시 격리된 NPG 환경에서 테스트하고 코드를 검토해야 한다.
- 벤더 부족분: 이 서버는 AI 에이전트가 생성한 "바이브 코딩" 코드로, 엣지 케이스나 버그가 있을 수 있다. 스키마에 있는 일부 엔드포인트(fail2ban 등 일부 기능)는 NPG 포크에서 404를 반환해 사용할 수 없다.
- 버전 고정: 배포 환경과의 호환성을 위해 mcp 패키지 버전을 특정 버전으로 고정했다. 무분별한 업그레이드는 FastMCP API 변경으로 인한 깨짐을 유발할 수 있다.

8. 맺음말
npg-mcp는 NginxProxyGuard라는 강력한 프록시 관리 도구를 MCP 생태계에 연결하는 실용적인 다리 역할을 한다. REST API를 표준화된 도구 인터페이스로 감싸고, 보안을 기본값으로 강화해, AI 에이전트가 인프라를 자연어로 안전하게 제어할 수 있게 해준다. 비록 바이브 코딩으로 빠르게 태어난 코드라 신중한 검토가 필요하지만, "AI가 인프라를 운영하는" 새로운 패러다임을 보여주는 좋은 예시다.
